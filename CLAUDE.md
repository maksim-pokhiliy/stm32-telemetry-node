# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Bare-metal C telemetry node on an STM32 Nucleo-F411RE: an MPU-6050 IMU and a BMP280 barometer on one I2C bus, telemetry streamed to a host PC over UART. Phase 2 puts a TF-Luna rangefinder on a pan servo and draws a live map of the room on the host. The repo is the author's public C learning log, written from scratch while learning C and the STM32 platform. Details, status and roadmap: `README.md`.

## Ground rule: study and review only

Every line of firmware here is hand-written by the author. The README says so, and the commit history has to keep it true. So:

- Never write firmware, a Makefile, a linker script, startup code, CMSIS/HAL glue, or an OpenOCD/st-link/gdb config for this repo. Not as a starting point, not as a reference to be rewritten. Phase 2 firmware (servo, rangefinder) is under the same rule.
- Never write hardware facts into the repo ahead of the author confirming them on the bench: pinout, I2C addresses, register values, baud rates, wiring. The `TBD` markers in the docs stay until the author reports the milestone done.
- Explaining a register, a bus protocol or a linker concept is study. A drop-in function, file or config is code generation. When the line is unclear, leave the artifact out and ask.
- Ground explanations in the STM32F411 reference manual and the sensor datasheets, cited by section, rather than in recall.
- Review the author's code the way a senior embedded engineer would: register semantics, timing, error paths, what the datasheet says versus what the code assumes. Quizzing is welcome.
- Docs edits are fine when they record what the author already did or decided.
- The language is "C", never "C/C++".
- Whether the host-side web dashboard (M9) may be AI-assisted is undecided. Ask before writing any of it.

The ceiling moves as the author learns. The README status section and the roadmap checkboxes say where it is now.

`.claude/hooks/guard-firmware-ceiling.sh` enforces the first rule: it blocks Write/Edit and Bash writes into `src/`, `*.c`, `*.h`, `*.s`, `*.ld`, Makefiles and debugger configs. If it fires, you were about to break the rule. Do not work around it.

## Build, flash, test

None yet. `src/` is empty and there is no build system. The planned toolchain (arm-none-eabi-gcc, make, gdb, st-link) is set up by the author in M1; do not scaffold it. When M1 lands, replace this section with the real commands as the author wrote them.

## Architecture and scope

Data path: sensors -> I2C -> Nucleo-F411RE -> UART -> host. Phase 2 adds the rangefinder (UART or I2C, decided at M8) and a servo driven by PWM; the host side becomes a web dashboard drawing the live map. Scope is bare-metal C with I2C, UART and timers/PWM. Out: RTOS, SPI, C++, flight control, a mobile platform (no odometry, no SLAM; `D-002`). Phase N+1 is discussed after phase N ships.

Driver layout, build setup, the telemetry frame format and the rangefinder interface are undecided. Each becomes a decision-log entry when it is made.

Milestones, in order: M1 toolchain bring-up and LED blink, M2 UART hello to host, M3 I2C bus scan, M4 MPU-6050 readout, M5 BMP280 readout, M6 framed telemetry stream; then phase 2: M7 servo sweep, M8 TF-Luna readout, M9 live map on a web dashboard. Status lives in `README.md`.

## Docs

- `docs/DECISIONS.md`: append-only log for choices that are expensive to reverse. One `D-NNN` entry per decision using the template in the file, appended under `## Log`. A changed mind is a new entry that supersedes the old one, never a rewrite.
- `docs/HARDWARE.md`: bill of materials, bench tools and wiring. Wiring is recorded only after the bench confirms it: M3 for the I2C sensors, M7 and M8 for the servo and the rangefinder.
