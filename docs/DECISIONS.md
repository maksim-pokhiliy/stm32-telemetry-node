# Decisions

Decision log for choices that are expensive to reverse: telemetry frame format, driver layout, build setup, host-side tooling, sensor and scope choices. One entry per decision, appended in order, never rewritten; a changed mind gets a new entry that supersedes the old one.

## Template

### D-NNN: Short title

- Date: YYYY-MM-DD
- Status: accepted (or: proposed, superseded by D-NNN)

**Context.** The situation that forced a choice, the constraints, the alternatives considered.

**Decision.** What was chosen and why.

**Consequences.** What gets easier, what gets harder, what to watch for.

## Log

### D-001: Phase 2 is a scanning rangefinder with a live map

- Date: 2026-09-29
- Status: accepted; the milestone numbering is superseded by D-003, the sensor choice and the scope stand

**Context.** The telemetry node (M0-M6) reads an IMU and a barometer and streams frames to a serial terminal. Correct, and dull to watch. The project needs a demo that carries a README gif and a short video on its own, and the host side should use the stack the author already knows, the web. A room scanner does that, and its first five links (toolchain, UART, bus, sensor readout, framed stream) are the M1-M6 roadmap verbatim; only the payload and the consumer change. Sensor candidates: HC-SR04 ultrasonic (cheap, wide cone that smears walls and corners into a submarine-movie radar), VL53L1X laser time-of-flight (I2C, room-scale range, an honest but soft outline), TF-Luna (single-beam rangefinder, the longest range and the narrowest beam of the three, UART or I2C).

**Decision.** Phase 2, milestones M7-M9: a TF-Luna on an MG90S pan servo sweeps the room, the firmware streams angle-distance pairs to the host as telemetry frames, the host draws a live map in a web dashboard. TF-Luna over the cheaper options because the map is the product and the beam width decides how it looks. MG90S over SG90 for the metal gears: less backlash, repeatable angles, a map that does not breathe. Phase 1 milestones and dates do not move; phase 2 starts after M6 ships. The rangefinder interface (UART or I2C) is decided at M8 and gets its own entry.

**Consequences.** New ground: timers and PWM for the servo, possibly a second serial link, and a separate 5 V rail so the servo does not brown out the Nucleo over USB. Hardware for both phases is ordered together (docs/HARDWARE.md). The wording stays "scanning rangefinder + live map": no "SLAM", no "lidar cartography", because there is no odometry and no pose stitching, and any embedded interviewer sees that gap in a second.

### D-002: No mobile platform

- Date: 2026-09-29
- Status: accepted

**Context.** With a rangefinder in hand the next idea is obvious: put it on a wheeled chassis and scan the whole flat. The chassis is a weekend: a kit, two motors, a driver board. The mapping is not. To place a measurement on the map the firmware needs the platform's pose at the moment of the measurement, and a cheap chassis has no way to know it. Wheel odometry drifts from the first metre (slip, wheel diameter tolerance, and no encoders on TT motors at all), a gyro heading drifts within minutes, and correcting either from a single-beam rangefinder is SLAM: a richer sensor, a graduate-level class of math, and a compute budget that in hobby terms means ROS on a Linux board, not bare-metal C on an F411. It would also break the story of this repo. The demo argument points the same way: a static scan gives a sharp room outline, a naively moving one gives doubled walls and a drift spiral. Three times the effort for a worse video.

**Decision.** No wheels in this project. The scanner stays on a static mount. If a phase 3 ever happens it is stop-and-scan: drive, stop, take a full static scan, send it as one frame, drive on. Every scan stays clean, SLAM is sidestepped, and the new skill is real: encoders and PID to drive straight and turn an honest 90 degrees. Rule for the project from here on: phase N+1 is discussed after phase N ships. Phase 3 is not discussed before M9 is done.

**Consequences.** Scope stays bare-metal C with I2C, UART and timers/PWM. The README avoids "SLAM", "mapping robot" and "lidar cartography". The vocabulary (odometry drift, dead reckoning, loop closure) is worth knowing anyway: "I understand why I did not do SLAM on an MCU with a single-beam rangefinder" is a better interview answer than a crooked robot on GitHub.

### D-003: Host side before the scanner

- Date: 2026-09-30
- Status: accepted; supersedes the milestone numbering of D-001

**Context.** D-001 put the scanner right after the telemetry node and left the host side for the last milestone. That leaves M6, the framed stream, validated only by a serial terminal, which shows bytes but checks neither framing nor checksums. It also builds the host pipeline and the scanner in one step, a big-bang integration at the very end. The host side is the author's native stack and the fastest part to build, and it is also the most comfortable place to overbuild.

**Decision.** Phase 2 is the host side: M7 a frame parser and a serial-to-MQTT bridge, built and tested on dumps recorded at M6; M8 live plots in the browser, with replay of a recorded session when the board is off. The scanner becomes phase 3: M9 servo sweep, M10 TF-Luna readout, M11 the live map in the same dashboard. Phase 1 milestones and dates do not move. Phases are defined by a shipped outcome, not by an activity: phase 1 ends when the board streams framed telemetry, not when the soldering ends. Phase 2 is time-boxed to the bridge, the plots and the replay: no auth, no database, no servers of the author's own.

**Consequences.** The protocol gets a real consumer while it is still warm, so framing and checksum mistakes surface before the scanner depends on it. When the scanner arrives, only the payload and one visualization are new. The full story, device to protocol to bridge to browser, exists after phase 2 even if phase 3 slips. The rule of D-002 ("stop-and-scan" is the earliest candidate for a phase 4) still applies, and its "M9" now reads M11.

### D-004: Firmware and host side live in separate repos

- Date: 2026-09-30
- Status: accepted

**Context.** The host side is a bridge process and a web dashboard sharing a frame parser. Options: a monorepo with the firmware, a GitHub organisation with one repo per tier, or two repos. This repo's premise is hand-written firmware; the host side is web code, where a different authoring policy is fine.

**Decision.** Two repos. This one stays pure C: firmware, decision log, hardware notes, and the demo gif with a link to the host repo. The host repo holds the bridge and the dashboard together, because they share the parser and the frame types, and nobody wants to publish a package for a parser of a couple of hundred lines. No organisation: that is a tool for a team or a brand, and a reader opens a repo, not an org page. The frame format is the contract between the two repos: the spec lives here in the decision log, and raw dumps recorded from the board are the fixtures the host parser tests against.

**Consequences.** Two toolchains, two CI setups and two READMEs stay apart, and the "hand-written" disclaimer of this repo stays absolute. The AI policy for the host repo is decided there. A protocol change is a two-repo change, which is the point: it forces the spec to be written down first.

### D-005: Host transport is a managed MQTT broker, replay first

- Date: 2026-09-30
- Status: accepted

**Context.** The demo should be viewable by someone in another city, and "switch the board on and it streams" is the goal. The board has no network interface, so the firmware cannot talk to a broker; the PC it is plugged into can. That is the standard node-gateway topology: a node on bare metal over UART, a gateway with the network stack, a broker, a browser. Candidates for the relay: a managed MQTT broker with WebSocket support, a self-written WebSocket relay on a rented server, a tunnel exposing the local bridge, or a realtime database. Live only works while the board and the PC are on, and a visitor opens the link when they are off.

**Decision.** The bridge on the PC publishes frames to a managed MQTT broker with a free tier; the dashboard subscribes with MQTT over WebSockets. One code path serves the desk and the remote viewer. The "API" is the topic layout and the payload schema, not REST routes. Publishing credentials live only in the bridge, the browser uses a read-only user, and a retained message carries the last frame. The dashboard is replay first: a recorded session ships with the static site and plays by default, labelled with its recording date; the view switches to live, labelled as such, when a stream is up. No database: browsing history is a later phase or never. No network on the board: a WiFi module and a TCP/IP stack in the firmware would be a phase of its own. The gateway can later become a small Linux board, so that "switch it on and it streams" is literal, with no firmware change.

**Consequences.** One hosted dependency, the broker, and its credentials to manage. Recorded dumps do quadruple duty: parser fixtures, offline development without the board, the public demo, and the replay mode. Firmware scope is untouched; the mistake to avoid is putting the MQTT client on the node.

### D-006: Hand-written peripheral register definitions

- Date: 2026-10-19
- Status: accepted

**Context.** Bare-metal firmware requires direct access to STM32 peripheral registers. Two approaches were considered: using CMSIS device headers from Arm/ST or defining the required register addresses and bit masks manually from RM0383. The repository is both a working firmware project and a public C learning log, where understanding the hardware and writing firmware independently take priority over development speed.

**Decision.** Use hand-written register definitions for Phase 1 (M1-M6), without CMSIS device headers or HAL. Define only the registers and bit masks actually needed by the firmware in `src/stm32f411_regs.h`, using names consistent with RM0383. Register addresses use the `_ADDR` suffix to distinguish them from register values. AI may assist with documentation lookup and explanations, but the author writes the definitions and verifies them against the reference manual and hardware.

**Consequences.** Every register address, bit position and mask must be understood and explicitly defined, improving familiarity with the STM32 memory map and peripheral architecture. The firmware remains fully hand-written without external device-header dependencies. The trade-offs are additional manual work, repetitive definitions and the risk of transcription errors. Register definitions must be checked against RM0383 and validated through debugging or hardware tests as peripherals are introduced. CMSIS remains a possible alternative for future phases if the maintenance cost outweighs the educational benefit.

### D-007: Source layout, build and the initial stack pointer

- Date: 2026-10-24
- Status: accepted

**Context.** M1 produced the first files that had to live somewhere: a linker script, startup code, a register header and a build. The layout was chosen on 8 Oct 2026 and is written up here at the close of M1. The alternatives were a vendor-style tree (CMSIS folders, a generated project, a `Startup/` directory with an assembly file) and a flat layout the author understands completely. The initial stack pointer needed a home too: the factory demo firmware on the board reports an initial SP of 0x20000560, a fixed-size stack placed right after its data, while the ST linker templates put the stack at the top of RAM.

**Decision.** Flat layout: the linker script `stm32f411re.ld` at the repo root, all C in `src/`, one module per `.c` and `.h` pair, the register header `src/stm32f411_regs.h` (D-006), a GNU `Makefile` at the root once the hand-typed commands stopped changing, build products in `build/`, which is gitignored. The build is `arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -Og -g3 -ffreestanding -Wall -Wextra` with `-MMD -MP` dependency files, linked through the gcc driver with `-nostdlib -lgcc -T stm32f411re.ld` and a map file, `objcopy -O binary` for the flash image, `st-flash write` at 0x08000000. The initial stack pointer is the top of SRAM, `ORIGIN(SRAM) + LENGTH(SRAM)` = 0x20020000, defined once in the linker script as `STACK_TOP` and referenced from C as an address: the stack grows towards lower addresses, so placed at the top it gets all of SRAM below it.

**Consequences.** Everything the chip executes is in files the author wrote, and `size`, `objdump` and `nm` on `build/firmware.elf` are the ground truth for what landed where. No startup assembly: the reset handler is C, with the vector table as a C array in its own section. The flat `src/` will need structure when drivers multiply; that is a later entry. `-nostdlib` means no libc and no C runtime: `-lgcc` is on the link line for the day a 64-bit division or a float needs a helper, and anything else (memcpy, printf) is written here or not used. The stack has no guard: it grows down towards `.bss` without warning, so stack depth is something to watch once interrupts and drivers arrive. The FPU stays off (`-mfloat-abi=soft` by default) until a decision at M5, when floats first appear.

### D-008: Drivers return one status type and bound every wait

- Date: 2026-11-16
- Status: accepted; the list of status values and the note that a timeout also covers bus errors are superseded by D-009, the rule stands

**Context.** I2C in M3 is the first peripheral here whose operations can fail because of the hardware: an address nobody answers, a wire that is off, a bus that is held low. The UART module from M2 cannot report a failure at all. Whatever shape the first failing function took, the sensor drivers of M4 and M5, the stream of M6 and the phase 3 drivers would inherit it, so the shape was chosen during M3 and is written up here at the close of the milestone. Three were considered: (A) one status enumeration for the whole project, returned by every driver function, with data going out through pointer parameters; (B) a `bool` result plus a global "last error" variable; (C) one integer in the Linux kernel style, zero for success, negative for an error, positive for a byte count.

**Decision.** A. `src/status.h` defines `status_t` with `DRIVER_OK`, `DRIVER_NO_ACK` and `DRIVER_TIMEOUT`. A driver function returns it directly, and future read functions hand their data back through output parameters. Success is `DRIVER_OK` rather than an I2C word such as "ack", because the type is shared by all drivers. The enumeration grows when a driver has a result that a caller will act on, not before. Time comes from the SysTick millisecond counter of M2; each module names its own limit as a constant, 5 ms per wait in the I2C driver. No new driver waits on a hardware state without a limit. An operation that failed reports its own failure even when the recovery of the peripheral that follows succeeds. B was rejected because the stored error can be overwritten by another operation before anyone reads it. C was rejected because it mixes a status, a byte count and, later, unsigned register data in one value.

**Consequences.** Every call site has to look at the result, and the M6 stream can report a silent sensor in a frame and keep running where an unbounded wait would hang it. The bound is only as good as the tick: a driver called before SysTick runs, or with interrupts masked, waits forever again, so a running tick is a precondition of every driver call. A limit of N ticks expires between N-1 and N milliseconds, because the start is sampled somewhere inside a tick: the 5 ms I2C limit is 4 to 5 ms against an address frame of about 0.1 ms at 100 kHz, and a limit of 1 could expire at once. A failed I2C wait costs its 5 ms plus the bounded waits of the recovery, which is what the main loop pays per dead device. `DRIVER_TIMEOUT` is an umbrella for now: an arbitration loss ends as a timeout and the bus error flag is not read; a separate value is added when a caller needs the difference. The UART module predates the rule and still waits on TXE and TC without a limit; that is revisited with the M6 stream. The enumeration is one byte in this build (short enums are the bare-metal ARM ABI default, `Tag_ABI_enum_size: small` in the ELF attributes), so it is an in-memory type: the frame format of M6 defines its own encoding for a status.

### D-009: The bus driver speaks registers, each sensor gets its own driver

- Date: 2026-11-23
- Status: accepted; refined by D-011, which moves the compensation of the BMP280 into its driver; the recovery has clocked a stuck SDA free since M5, so the sentence on UM10204 3.1.16 below describes M4

**Context.** M4 reads the first sensor, and the BMP280 of M5 hangs on the same bus. Both chips are a table of 8-bit registers. A write is the device address, a register address and a data byte. A read is the device address, the register address, a repeated START, the device address again and then the data bytes, with a NACK from the controller on the last one. On the STM32F4 the end of a receive is three different sequences, for one byte, for two and for more than two (RM0383 18.3.3), and a wrong one leaves the bus held. The question was where that knowledge lives and what a sensor driver calls. Three shapes were considered: (A) the bus driver exposes register operations, write one register and read N bytes starting at a register, and builds each transaction itself; (B) the bus driver exposes raw transfers, write bytes with or without a STOP and read bytes, and every sensor driver assembles its own transactions; (C) the sensor driver works on the I2C1 registers directly. Two smaller questions rode along: whether sensor drivers get a status type of their own, and whether a sensor driver returns raw counts or physical units. The choice was made in the first session of M4, before the first register function, and is written up here at the close of the milestone.

**Decision.** A. `src/i2c.h` grows `i2c_write_reg(dev_addr, reg_addr, value)` and `i2c_read_reg(dev_addr, reg_addr, buf, len)`. The device address is the unshifted 7-bit address, the register address is one byte, and a read takes any length from one byte up and picks the receive ending itself. The repeated START, the flags, the three endings, the STOP and the recovery stay in `src/i2c.c`. `src/mpu6050.c` knows the register map and the data format of the sensor, calls the two bus functions and touches no STM32 register. It includes `i2c.h` directly: there is no replaceable transport underneath, and none is claimed. The sensor driver returns raw counts: `mpu6050_read_sample` fills a struct of seven `int16_t`, three accelerometer axes, the temperature and three gyroscope axes in register order. Scaling, calibration and filtering are not the driver's job, and the temperature conversion sits in the application. A sample is handed over whole or not at all: the 14 bytes go into a local buffer and the caller's struct is written only after a successful read. The status type stays the one of D-008 and grows the way D-008 said it would, by results a caller acts on: `DRIVER_NO_ACK` becomes `DRIVER_NO_ACK_ADDR` and `DRIVER_NO_ACK_DATA`; `DRIVER_INVALID_ARG` answers an address above 0x7F, a null buffer or a zero length before the bus is touched; `DRIVER_WRONG_ID` means the identity register did not hold the expected value; `DRIVER_BUS_ERROR` reports the bus error and arbitration lost flags, which D-008 had left under the timeout. B was rejected because every sensor driver would repeat the fragile part, the STOP and the receive ending. C was rejected because it mixes the two layers. A separate status type for sensor drivers was discussed and dropped: one type keeps every call site the same.

**Consequences.** The BMP280 driver of M5 needs no new bus code. The interface fits devices with this register model and nothing else: a device with 16-bit register addresses, or a transfer with no register pointer, needs a new bus function. When a read fails after it has started, the caller's buffer may be partly written, so a caller that must not publish half a result reads into a buffer of its own, as the MPU-6050 driver does; that guarantee covers sequential code, not a reader in an interrupt. The numeric values of `status_t` moved with the new members (a timeout was 2 and is 3), so a number in an old log is read against the enumeration of its day, and the M6 frame defines its own encoding, as D-008 already says. The recovery is still a reset of I2C1 inside the MCU: it does not clock free a target that holds SDA low (UM10204 3.1.16), and it does not put a sensor that lost its power back into its configuration. The sensor driver relies on the measurement ranges the chip has after its own power-on and does not write them; a reset of the board alone does not reset the sensor.

### D-010: Module boundaries, two boot modes in one image, one time API

- Date: 2026-11-27
- Status: accepted

**Context.** By the end of M4 `src/startup.c` was 1189 lines: the reset handler and the vector table, the SysTick handler and its set-up, the temperature conversion, the bus scan, the 712-line bus self-test, the stream, the report and `main`, plus four experiments nothing called. The self-test ran on every boot after the sensor driver had configured the MPU-6050, took about 0.8 s and wrote the sensor's power register 204 times. The tick was a global that any module could write, and two modules each had their own delay loop. M5 adds a second sensor, so the file was split first, on 24 and 25 Nov 2026, and the choices are written up here at the close of the milestone. For the bench tests two shapes were on the table: (A) a build parameter, so that the default image carries no tests, which the reviewer had suggested; (B) one image that always carries the tests and chooses at boot whether to run them.

**Decision.** The modules: `src/startup.c` keeps the reset handler with the `.data` and `.bss` set-up, the default handler, the vector table and the call of `main`. `src/systick.c` owns the millisecond counter as a private `volatile uint32_t`, together with `SysTick_Handler`, `systick_init`, `systick_get_ms`, `systick_elapsed_ms` and `systick_delay_ms`. `src/app.c` holds `main`, the periodic tasks, the output and the statistics. `src/selftest.c` holds the diagnostics and the bench tests. `src/conversions.c` holds the arithmetic of the MPU-6050 temperature conversion and touches no hardware. The UART module, the I2C driver and the sensor drivers stay separate modules. For the tests, B: one image with two boot modes. NORMAL is the default. SELFTEST is selected by holding the USER button (PC13, low when pressed) during reset, and the button is read once. After the tests both sensors go through their normal init, and the tests are not run when `i2c_init` failed. Time has one API: a caller reads the counter only through `systick_get_ms`, measures with `systick_elapsed_ms(now, start)` and waits with `systick_delay_ms(n)`, which for a positive n returns once more than n ticks have passed, so that the phase of the tick cannot shorten the delay. Zero returns at once, and `UINT32_MAX` is not a valid duration. The delay needs a running SysTick and enabled interrupts.

**Consequences.** The image that passed the tests is the image that runs, and the tests no longer touch a sensor after its driver has configured it. The default boot reaches the first sample 219 ms after reset; the self-test mode takes about 1.09 s. The price is flash: `i2c_selftest` is 4284 of the 13848 bytes of the M5 image whether it runs or not. The button means something only at reset, and later presses are ignored. No module can write the tick any more. The two conventions for time differ and are easy to mix up: a timeout of N in the I2C driver expires between N-1 and N ms (D-008), a delay of N lasts between N and N+1 ms. `systick_delay_ms(UINT32_MAX)` would never return, which makes it the one wait whose bound depends on the caller keeping the contract; D-008 forbids unbounded waits, so no caller may compute a duration that can reach that value. `SysTick_Handler` is defined in `systick.c` and referenced by the vector table in `startup.c`, which declares it for itself. `src/app.c` is where the M6 framing lands, and the text lines it prints now are what the frame replaces.

### D-011: BMP280 configuration, and its compensation lives in its driver

- Date: 2026-11-27
- Status: accepted; refines D-009

**Context.** The BMP280 hands over two 20-bit raw values that mean nothing on their own: turning them into a temperature and a pressure takes twelve calibration words stored in the chip and the formulas of its datasheet (BST-BMP280-DS001 rev 1.26, 3.11.3), and the pressure formula needs an intermediate value of the temperature formula. D-009 had said that a sensor driver returns raw counts and that scaling and calibration are not its job, which was written with the MPU-6050 in mind. The sensor also had to be configured: forced or normal mode, the oversampling of each measurement, the filter and the standby time, for which the datasheet offers ready rows (Table 15), and the arithmetic had to be picked among the 64-bit integer formula, the 32-bit one (8.2) and the floating-point one (8.1). The author made the choices on 26 Nov 2026, and they are written up here at the close of M5.

**Decision.** The sensor is the one at address 0x76 with id 0x58. It runs in normal mode with the settings of the datasheet row "handheld device low-power": pressure oversampling ×16, temperature oversampling ×2, IIR filter coefficient 4, standby 62.5 ms, written as 0x28 to `config` and 0x57 to `ctrl_meas`. The nominal output rate is 10 Hz, and the application polls every 100 ms without synchronising to the sensor, so a poll may see the same measurement twice or skip one. `bmp280_init` resets the sensor by command, waits 2 ms and then polls `im_update` within a budget of 5 ms. The calibration is private to `src/bmp280.c`; a getter returns a pointer to const, and NULL until the init has succeeded. Raw counts are `uint32_t`. The temperature comes out as `int32_t` in hundredths of a degree Celsius by the 32-bit formula, the pressure as `uint32_t` in Q24.8, that is in 1/256 Pa, by the 64-bit formula. The compensation is pure arithmetic inside `src/bmp280.c`: it takes the calibration as a parameter and keeps `t_fine` local. `bmp280_compensate` computes the temperature and the pressure of one raw sample and writes the result only if both succeeded. This refines D-009: the calibration and the compensation that are specific to the BMP280 belong to its driver, and the raw counts stay available to the caller.

**Consequences.** The application gets physical units from the barometer and raw counts from the MPU-6050, whose one-line conversion stays outside its driver, so the two drivers no longer follow the same rule and D-009 is read together with this entry. A 64-bit division is not an instruction on this core: it pulls `__udivmoddi4` from libgcc, 700 bytes, and the pressure function itself is 506. No floating point entered the firmware, so the FPU question that D-007 left for M5 stays open. The formulas shift negative values to the right, which C leaves to the implementation; the driver pins the behaviour it needs with static assertions and writes the left shifts of values that can be negative as multiplications. With the calibration of this unit no raw value can overflow an intermediate; with arbitrary corrupted coefficients that is not guaranteed. The exact integer result for the datasheet example is 25767233, three counts below the 25767236 printed in the figure of 3.12, and the self-test expects the former. The polling is not synchronised, and the standby time of the sensor is specified only to ±25% (Table 2), so the stream cannot promise one fresh measurement per sample. An identical pair of raw values proves nothing either way: at the acceptance the filtered output repeated by coincidence about one time in eight. A sensor that was reset, or whose measurement is skipped, delivers 0x80000, which the compensation accepts as a valid input. What makes a sample valid, and how a frame says so, is decided with the M6 frame format.
